## 1. 调研背景与目标

AI 投研平台的 Agent 应用存在两种运行模式：**聊天模式**与**研究模式**。项目目标是建立一套可复现的评测基座，从真实运行日志中量化 Agent 工作流的表现，回答四个问题：

- 省不省：Token 与成本消耗结构；
- 稳不稳：工具调用行为与失败模式；
- 快不快：端到端与分阶段时延；
- 对不对：理解、路由、参数、陈述等过程质量。

## 3. 核心发现

### 3.1 成本瓶颈不在回答正文，而在"模型—工具循环"与重复上下文

初始实勘结论：聊天模式 Token 消耗与模型步骤数的相关系数约 **0.9645**、与工具调用数约 **0.9492**；研究模式绝大多数 Token 为缓存读取。
针对这一个问题，主要从工具调用、成本维度、时间维度来完成评测。

### 3.2 数据观测缺口（实勘确认）

- 聊天模式 `tool_result` 无任何 status/error 字段，无法判定调用成败；
- 两模式全库 0 个 retry/attempt 键，无法识别重试链；
- 聊天模式全无消息级时间戳，端到端时延只能用秒级边界推导；

## 5. 主观评测（人工 or LLM Judge）难题

在 Agent 多路召回与上下文拼合的架构下，开展回答证据支持率（Claim Support Rate）校验的核心困难可总结为以下五点：
- 归因难：多路源头（数据库、搜索引擎、API 等）交织，当回答出现偏差时，难以判定是大模型自身的生成幻觉、多源数据间的互相矛盾，还是某一路源头数据本身失真。
- 定位难：信息拼合与二次提炼会破坏原始文档的结构和元数据（Metadata）。回答中的断言（Claim）缺乏明确的上下文锚点，导致评估器在比对时需要在海量拼合文本中盲目搜索，极其容易匹配失效。
- 判定难：多路召回不可避免带来大量冗余与无关信息。评测模型（LLM-as-a-Judge）面对长文本时容易注意力分散，仅因上下文提及了相关实体便误判为“有证据支撑”，从而掩盖无证据支持的错误。
- 校验难：Agent 在拼合多路信息时常执行“跨源隐式推理”（如结合 A 接口的数值与 B 接口的规则得出结论）。此类合理推论在任何单一原始切片中均无原文对应，极易被静态比对算法误判为“无证据支撑的幻觉”。
- 成本高：计算证据支持率需要将回答拆解为多个元断言，并分别与庞大的拼合上下文做自然语言推理（NLI）比对。这种二次检索与高频 LLM 调用会导致评测环节的计算延迟和 API 成本远超 Agent 运行本身。
