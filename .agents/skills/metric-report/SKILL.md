# Metric Report

生成研究模式指标宽表的自包含 HTML 报告(图表内嵌 base64 PNG),单数据源为
`data/processed/metric_table_full.csv`,零回源(不访问 OSS)。

> **本文件只写"怎么生成"**:数据源、运行方式、报告结构、列集与阈值契约、维护同步点。
> **不写任何本样本的统计结果**——命中数、占比、工具名排名、富集倍数、模型清单等一律以
> 脚本实时渲染为准。本文件里出现的数字**只有两类**:代码里的固定常量(条数 / 截断 /
> 分档边界)与"有多少个常量"这类结构信息,它们改代码就会变;核报告时看渲染结果与代码常量,
> 不要从本文件引用任何样本结论。

## 何时使用

用户要求:出指标报告、两版指标对比、工具耗时/Token 占比排名、分位数统计、
bad case 洞察、Agent 迭代建议——且已有 `metric_table_full.csv` 宽表。

## 前置

- 数据源:`data/processed/metric_table_full.csv`(4 身份列 + 注册表全部指标列)。
  列集变了要同步 `scripts/generate_report.py` 的四个列集常量:
  `SCALAR_COLS`(标量)、`PER_TOOL_COLS`(逐工具 JSON 列表)、`JSON_SCALAR`(参与稳定性
  与高危判定的单元素 JSON 列)、`JSON_EXTRA_COLS`(只进第 0 节可计算性清单的其余 JSON 列)。
- 绘图依赖 matplotlib + numpy,**项目 venv 未装,须用 anaconda python**:
  `C:/Users/EDY/anaconda3/python.exe`。
- 中文绘图字体配置为 Microsoft YaHei 优先(SimHei 无 bold 字重,加粗会静默回退)。

## 运行

```
"C:/Users/EDY/anaconda3/python.exe" -X utf8 \
  .agents/skills/metric-report/scripts/generate_report.py \
  --csv data/processed/metric_table_full.csv \
  --output reports/metric_report.html \
  --data-range YYYYMMDD-YYYYMMDD
```

产出 `reports/metric_report.html`,浏览器直接打开,图表内嵌、无外部依赖。

**`--data-range` 必填**(2026-09-24 需求方要求):报告表头必须标明本批次日志的
数据日期区间。宽表只有身份列 + 指标列、**不存日期字段**,无法从 CSV 推导,故每次出报告
都要由调用方按本次导出清单的实际日期范围显式传入。脚本对缺失/格式不符会直接报错退出,
不静默降级——没有数据日期的报告不允许产出。**脚本只校验格式、无法校验正确性**,
传错不会报错,只会静默出一份日期错误的报告,核对时须与本次导出清单实际区间比对。

## 报告结构(六节)

> 条数 / 截断 / 分档的权威清单见下方「报告统计细节速查」表;与本节的散句冲突时以速查表
> 及其标注的代码常量为准。

0. **样本与可计算性** —— 日志总数/用户数/会话数/模式/数据源文件 + 逐指标可计算日志数表。
   覆盖列 = `SCALAR_COLS + PER_TOOL_COLS + JSON_SCALAR + JSON_EXTRA_COLS`;
   取值形态三分固定为 整数 / 浮点数 / JSON。本节含**列集漂移自检**:反向比对宽表表头,
   未被任何常量覆盖的列以红字提醒同步(它兜底"漏列",兜不住"条目数写错")。
1. **两版指标横向对比** —— 三列表格(保留 / 删除 / 新增,只写中文指标名),下方附
   新增指标的"含义与取值举例"注释表。列头括号里的条数由 `EVOLUTION_KEPT` /
   `EVOLUTION_DELETED` / `EVOLUTION_ADDED` 三个列表长度实时决定(改列表即改列头),
   下方"旧版 = 保留+删除、现版 = 保留+新增"两句注同样按 `len()` 生成。
   注释行数须等于 `ADDED_NOTES` 行数。
2. **宽表指标统计总结**
   - 2.1 标量指标 p50/p80/p90/p95/p99 表:只列 `SCALAR_COLS` 中 `in_quant=True` 的列;
     比率列按百分比两位小数,整数列千分位整数。
   - 2.2 四宫图 2×2:每行一个指标(总 Token / 总时延),左列等宽分箱频次直方图
     (纵轴上界截断到 p99 屏蔽离群值,未入图条数红字标注),右列只画 p50/p80/p95/p99
     虚线刻度线 + 加粗数值标签(不加白底、不画条形),两列共用同一线性数值纵轴。
   - 2.3 稳定性信号分布图 + 表:信号清单以 `build_stability_signals()` 的 `specs` 为准
     (改信号只改 `specs`,图与表同源)。表只展示**原始计数**——命中日志数 / 占比 /
     其中未闭环,**不展示派生倍数**(倍数由 4.2 统一给出,避免两处口径漂移)。
     信号为日志级:一条日志可同时命中多个信号,各行不可相加。
3. **分布与排名**
   - 3.1 工具耗时排名:图(按均值)+ 表(出现日志数 + 各分位 + 均值)。图与表条数不同,
     不要互相对齐。
   - 3.2 工具使用频率排名:纵轴为"出现该工具的日志数",条尾标 `N 条日志(M%)`,
     避免误读成调用次数。
   - 3.3 工具错误归因(`tool_error_attribution`):图一 = 归因分布(四类穷举)+ 工具
     错误量;图二 = 失败率 + 逐工具归因堆叠。见下方「3.3 工具错误归因」。
   - 3.4 模型层错误分类与路由:分类按 `LLM_ERROR_CLASS_CATALOG` **穷举**(零命中类也列出);
     模型列出宽表里出现过的全部模型(含零错误)。分类占比与模型出错率是两个量纲,不可横向比较。
   - 3.5 框架 API 重试归因(`api_retry_attribution`):双栏 = 按工具 + 按接口。
4. **bad case 洞察** —— 死亡日志(故障)vs 高危日志(消耗)双主体归因 + 工具热点 +
   4.5 步数分档风险曲线(5.3 刹车建议的依据)。
5. **Agent 迭代建议** —— 止血 / 降本 / 提效三层递进,数字由脚本实时计算注入。

## 已知偏差(改报告时必须一并处理)

这些是**已确认存在、尚未修复**的问题,不是设计意图。核报告时不要把它们的输出当成实时结论。

1. **`presence['scheduler_task']` 是直接下标**(`chart_tool_error_rate_and_matrix` 的文案),
   该工具一旦在换样本后缺位,脚本抛 `KeyError` 而非降级。同函数文案还写死了几组工具名
   及其归因倾向——**数字实时算,工具名是字面量**;换样本后这些字面量可能与实际排名不符。
2. **4.4「最高频工具全是文件/检索类基础操作」是写死的归类判断**:实际最高频工具里可能包含
   非文件/检索类的工具(如技能加载类),措辞与数据可能不符。"工具面广(N 种)"实时算,
   但归类结论写死。换样本后必须重新核对这句。
3. **3.3 图二文案把"失败率高"表述成"又常用又爱坏"**:失败率高的工具未必是出现日志数高的
   工具,常用性判断不成立,应退化为只谈失败率。
4. **3.5 图标题的 "Top8 / Top5" 是请求条数,不是实际渲染行数**:两栏实际行数 =
   跨行汇总后的 distinct 数,可能少于请求条数。另注意两级截断:单元格产出时
   `summarize_metric_table.py` 的 `build_attribution_cell` 已执行 `_topk(k=5)`,
   报告再聚合——**若某行 `by_tool` 超过 5 个条目,第 6 名起的重试数会被静默丢弃**,
   届时"按工具合计"会小于 `api_retry_count` 总量。数字实时算,但读者会以为该维度
   有 8/5 个候选。
5. **`charts["tool_token_rank"]` 算了但从不渲染**(`main()` 里构建,HTML 模板没有引用它),
   单工具 Token 表 `tool_tables["per_tool_call_tokens"]` 同样未出表。这是**故意还是漏删
   目前无据可查**(报告结构里从来没有"工具 Token 排名"一节)。每次出报告都白跑一次
   `collect_per_tool` + 一次绘图。清理前先问需求方:要么补一节,要么删掉这两处构建。

## 术语约定

- 全报告统一以**日志**为计数单位,**不使用"回合"计数**:文案写"X 条日志 / 日志数",
  表头写"出现日志数 / 日志数"。
- 例外:指标名保留权威口径原名"回合完成率"(`初步入库评测指标.md` 7.1),不因本约定改名。
- 第 4/5 节的洞察数字必须由脚本实时计算,禁止硬编码常量。唯一允许写死的只有
  **口径阈值与分档边界**这类"判定规则"本身:`HIGH_BE_THRESHOLD` /
  `HIGH_TOOL_ERROR_THRESHOLD`(高危门槛)、2.3 的 API 重试率信号阈值(取全可计算口径分位)、
  `STEP_BANDS`(步数分档)、`HIGH_CONSUMPTION_PERCENTILE`(高消耗分位)。它们都是**规则**,
  改动须走「关键口径」的同步流程;任何**统计结果**(倍数、占比、均值、工具名清单)
  都不许写死。

## 关键口径(以本文件为落点,阈值改动须同步代码与 AGENTS.md 的行动项)

- **高危日志**(报告第 4 节与 bad case sheet 共用口径)= 闭环 ∧ (业务错误数 be ≥
  `HIGH_BE_THRESHOLD` ∨ 工具错误数 te > `HIGH_TOOL_ERROR_THRESHOLD`)。
  **死亡日志** = `turn_completion_rate == 0`。阈值定义在两个地方,必须同步:
  `.agents/skills/metric-report/scripts/generate_report.py` 与
  `scripts/build_badcase_workbook.py` 的同名常量。报告与 sheet 的高危口径不允许分叉
  (bad case Excel 的产出脚本见 `docs/runbooks/04-build-badcase-xlsx.md`)。
  te 门槛补的是"错误分散在多个工具、每条都不重"的场景,be 门槛抓不到。
- **高消耗富集** = P(Token ≥ 全样本 p90 | 命中) ÷ P(Token ≥ 全样本 p90)。
  阈值常量 `HIGH_CONSUMPTION_PERCENTILE`。⚠️ **它与"死亡富集"分母口径不同**
  (一个是 Token 分位、一个是未闭环率),文案里并列出现时必须**分别标注量纲**——
  历史上正因为没标注而无法解释、且换口径后无法复现。
- **死亡富集** = P(未闭环 | 命中该信号) ÷ P(未闭环 | 全样本),基线由 `base_death_rate`
  单点计算后贯穿全脚本,**禁止各节各算一份**。它不展示为列,只作为**内部排序/论证**
  用于 4.2(为何取这两个门槛)、5.1(按富集排加固工具)、3.4(模型错误致死性对比基线)。
- **重试次数**指框架/工具传输层 API 重试(同一 `(callID, endpoint+入参指纹)` 重复,
  `fingerprint_dup_v2`),**不是模型级(LLM)重试**;模型级重试属埋点 D 当前不可观测,
  禁止混称。同理 `requestId` 尾序号是"调用内第 N 个请求"的工作流深度信号,不是重试次数。
- 指标列集以 `scripts/summarize_metric_table.py` 的 `build_metric_columns()` 为唯一事实来源;
  `per_tool_repeat_call_count` / `mcp_tool_call_inflation_rate` / `citation_traceability_rate`
  已退出宽表(评测器保留)。报告改列集时按下方「维护」同步四个列集常量,不要按记忆写死列数。
- 模型出错率的分母来自 `llm_error_count` 单元格的 `total_call_count` / `model_calls`
  (评测器 1.3.0 起),**不是**逐工具 JSON 那类可推导的分母;旧表缺该键时报告如实标注
  "调用数待补",不得用错误数硬算。
- 两列归因的**留空含义不同**,文案不得混用:零错误 / 零重试的日志在
  `tool_error_attribution` / `api_retry_attribution` 上留空,留空表示"没有该类事件",
  **不等于**该列指标为 0 或不可计算。
- 第 4/5 节的**所有**数字必须实时计算(含工具名清单与均值),禁止写死;需要新数字时
  在 `main()` 里先算好变量再插值,不要直接把样本结论敲进 f-string。
  这条规则目前**仍有 3 处已知违反**(工具名字面量、4.4 归类判断、`scheduler_task` 直取),
  逐条列在「已知偏差」;核报告时先看那一节,别把遗留的写死文字当成实时结论。
